# Owned local Java server manager

## Implemented source scope

The Minecraft servers destination provides an owned inventory, typed creation fields, explicit edition/distribution/target selectors, memory and port steppers, file pickers, explicit EULA consent, version discovery and local start/stop/restart actions. Official vanilla Java has local Windows-process and bounded local Docker adapters in source. SSH process and SSH Docker remain visible with unavailable reasons. Bedrock installation remains unavailable.

Refresh obtains the complete official Java manifest from `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json`, including returned historical and snapshot entries. Selecting a version obtains its metadata and verifies the manifest SHA-1. Metadata requests allow fixed official HTTPS hosts, reject redirects and embedded credentials, limit responses to 4 MiB and time out after 15 seconds. Cancel invalidates pending generations. Offline responses retain the existing choices with an explicit status; no catalogue is persisted in this unit.

A version is eligible only when metadata provides a server digest/size and a Java major version. Missing historical server/runtime fields are unavailable, not guessed. The user selects a Java executable and already downloaded server JAR. Creation verifies the JAR size and SHA-1 against official metadata, copies from its verified handle, rechecks copied bytes, and creates a new UUID-owned directory. It writes explicit accepted EULA and selected server port. It never adopts existing worlds or directories. Failed partial creation retains its owned directory for recovery.

The manager stores a versioned inventory below application-local data. Existing unknown document/record fields are preserved. Both creation preflight and save reject inventories above 256 records or 1 MiB of serialized JSON, including unknown fields. The proposed appended record is checked before creating its directory. A malformed inventory blocks creation rather than replacing it. Every existing path ancestor is checked, including inventory, runtime, source JAR and managed destinations. Symbolic links and Windows reparse points (including junctions) are rejected. Local Windows drive paths only are supported; UNC/device paths and alternate streams are unavailable. Managed writes and launches additionally require canonical containment. Checks are repeated before operations, but path-based APIs cannot eliminate a hostile concurrent rename/reparse race; handle-relative filesystem operations are not implemented. Start revalidates the JAR digest and runtime path and executes an argument list through QProcess. Only processes created by this manager are controlled. Started means an owned process/PID exists, not game readiness. Stop sends the stop protocol line to that exact process; restart waits for exit and restarts the captured server identity independently of later list selection. Closing the manager requests graceful stop; QProcess destruction ends remaining owned children. No unrelated process is discovered or adopted. Logs are discarded in this bounded unit.

## Limits and incomplete coverage

This is a first implementation unit, not a complete universal server manager. Runtime major-version compatibility, executable provenance/digest, port availability, readiness, capacity and native lifecycle acceptance remain unverified. Creation performs bounded local hashing/copying synchronously. Runtime provisioning, distribution download, transactional rollback of partial creation, version/channel filtering, searchable selectors, per-version property descriptors, Bedrock/history, complete container workflows and SSH adapters, mods/plugins/packs, worlds, backups, users/permissions, schedules, management APIs, exports and full GUI contracts remain incomplete. The memory range is a manager safety limit, not a claim about every version's supported resources. Unknown inventory fields survive serialization; existing server configuration is not adopted or edited.

English/Cantonese/bilingual voice keys are supplied separately for integration. Docker controls, target/edition/distribution selectors, file filters, action captions, contextual accessible names and lifecycle state messages use the shared voice catalogue and refresh live without changing selection, query or inventory. Catalogue integration and native language/accessibility acceptance remain pending for this source unit. Guidance, advanced appearance, history, bulk actions, anchored regex filtering and server-specific status reporting need follow-up. No real server, metadata request, license acceptance or process launch was exercised during implementation.

## Local Docker adapter

The local Docker route uses the same Mojang-verified server JAR and explicit Minecraft EULA choice. Its separate CLI picker accepts a local `docker.exe` or `docker` file. The adapter binds the CLI to the local Docker Engine endpoint rather than inheriting a context or remote `DOCKER_*` selection. It does not install Docker, pull images, accept a license automatically, adopt existing containers, remove containers, prune resources or change host power settings.

Runtime discovery obtains the selected Java major's `*-jre` tag metadata from `https://registry-1.docker.io/v2/library/eclipse-temurin/manifests/`. Adoptium identifies Eclipse Temurin as its Docker Official Image. The trusted registry namespace is `docker.io/library/eclipse-temurin`; the publisher reference is the Eclipse Adoptium container project. The fixed provider route obtains anonymous public read authorization from `auth.docker.io`, retaining it only in memory for the next registry request. No user credentials are requested or stored. Each authorization and metadata request has a reply-owned 15-second absolute deadline in addition to the 15-second inactivity timeout. The selected tag index must fit 4 MiB within that deadline, use schema 2 and an accepted OCI/Docker index format, match its `Docker-Content-Digest` SHA-256 header and contain at most 256 platform records. Redirects are rejected. Eligible entries retain their immutable SHA-256 digest, Linux architecture, Java major, source URL, verified index digest and retrieval timestamp. Only Linux amd64 and arm64 metadata are accepted. This is a bounded provider adapter, not complete historical runtime discovery.

Before creation, start or restart, the manager reads the local daemon's operating system, architecture and reported memory, then inspects the exact installed digest. The local image must advertise the same repository digest and platform and a strictly parsed `JAVA_VERSION` matching the selected major. The exact runtime version is retained with the server record. Registry HTTPS metadata establishes the provider namespace and published digest; local inspection establishes matching installed identity. This does not authenticate a hostile Docker daemon or independently verify the image's publisher signature. Missing metadata or a missing/incompatible local image remains unavailable. No image bytes were downloaded during implementation.

The container is created without starting, with `--pull never`, a UUID-derived name, inventory/server ownership labels, one managed data mount, explicit Java entrypoint and fixed JAR arguments, selected memory and port, loopback-only published TCP port, bridge networking, dropped capabilities, no-new-privileges, a PID bound and disabled Docker log retention. Creation's returned full container ID must be saved atomically before start. An existing container with the same name is not adopted. Persistence or cancellation after creation can leave a stopped owned container requiring explicit recovery; automatic adoption and removal are not implemented.

Start, stop and restart capture the server UUID. Every mutation first inspects the saved full container ID and verifies its ID, name, image reference, ownership labels, data mount, Java arguments, network mode, memory and port mapping. A mismatch sends no lifecycle action. Stop requires a safe local CLI, saved full container ID and record ownership, then the same exact container/configuration inspection. It does not require the original JAR, a still-installed launch image or sufficient memory for a new launch. Stop uses Docker's container stop protocol, with a 30-second shutdown interval configured at creation; only the exact verified owned container can be affected. The adapter keeps containers across manager closure. Docker CLI requests time out after 40 seconds, retain at most 256 KiB of output, discard stderr and never display raw diagnostics or image environment metadata. Cancellation ends only the owned CLI request; it does not assert that a daemon-side operation was rolled back. A lost connection leaves state unknown, never falsely stopped.

Docker Desktop may report a translated Linux mount path for a Windows bind source. This unit accepts only an exact normalized source-path match and reports other mappings unavailable. Docker Desktop mount translation, actual port conflicts, memory overhead, permissions, readiness, graceful server shutdown and container lifecycle remain pending native acceptance. Registry metadata caching/offline discovery, image provisioning, signature verification, SSH targets, Bedrock, other flavors and the full management workflows remain incomplete.

## Docker language and accessibility inventory

The bounded Docker copy inventory contains 40 shared catalogue entries: 30 under `server.docker.*`, four target labels, two edition labels, one distribution label and three file-filter labels. English, Cantonese and bilingual modes use the same stable keys. Lifecycle messages retain their key and factual suffix, so a language change refreshes the current state rather than replacing it with a generic ready message. Digest, platform and runtime identifiers retain their exact technical values. Accessible button names follow their visible captions; generic file-picker buttons also name the field they act on.

`dockerCopyInventoryAndLiveLanguageChanges` carries the explicit 40-key inventory, checks all five levels in all three modes, and exercises actual bound controls, selectors, current lifecycle copy and accessible names. It verifies that translation changes preserve selected target/version/image, image metadata, search text, selected/filtered inventory and the persisted document without emitting selection-change signals. Its execution requires the separately integrated catalogue additions. No test or native accessibility execution occurred in this unit. The wider manager's remaining guidance, responsive layout and complete language coverage are not implied by this bounded inventory.
